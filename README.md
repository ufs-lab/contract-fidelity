# contract-fidelity

**Find defensive code written against guarantees your API contract already
gives — and the type widening that made it look necessary.**

```ts
// contract: Movement.amount — "Amount in minor units (must be > 0)"
function formatAmount(amount: number): string {   // guarantee dropped here
  if (amount > 0) return `${amount}`;             // ...defended here
  return "-";                                     // dead branch
}
```

Two checks over a generated OpenAPI TypeScript client and the code that
consumes it:

| Command | Reports |
| --- | --- |
| `contract-fidelity dead-code` | a guarantee was dropped **and** something downstream defends against a value that can never arrive |
| `contract-fidelity widening` | the widening **alone**: a declaration wider than the contract value flowing into it |
| `contract-fidelity contracts` | audit — every guarantee the tool believes it read |

## Install

```bash
npm install --save-dev contract-fidelity   # typescript is a peer dependency
```

```json
// contract-fidelity.config.json
{
  "contractPackages": ["@acme"],
  "tsconfig": "tsconfig.json",
  "scanRoots": ["src"],
  "trustContract": true
}
```

`contractPackages` is required and has no default: a scan that matches nothing
would report "clean" while checking nothing. A value matches both
`node_modules/@acme/...` and pnpm's `node_modules/.pnpm/@acme+...`, and a bare
directory name matches an in-repo generated client.

Both checks keep a **down-only baseline** in `.contract-fidelity/`, so an
existing backlog can be adopted without blocking every commit, while anything
new fails.

## Status, honestly

Precision is validated: run against three unrelated public SDKs generated by
`openapi-generator` — Lob, Conekta and Klaviyo, ~4,850 contract guarantees
between them — it reported **zero false positives**. Doing that found four
portability bugs that the originating codebase could never have shown, all
now regression-tested.

Recall is **not** validated outside its home codebase. Those three SDKs are
thin wrappers with no view models, so it found no true positives in them
either. If you run it on an application that consumes a generated client, the
result is genuinely interesting — please open an issue either way.

The prose heuristics (`must be > 0`, `1-31`) are tuned to descriptions
`openapi-generator` emits; other generators word things differently. The
required-non-null and enum detection is generator-agnostic and carries most of
the value in practice.

## The contract is trusted

The generated clients are the source of truth. Re-deriving at runtime what a
contract already states is a bug, not prudence — it forks the code on a branch
that cannot execute, and hides which value is really authoritative:

```ts
if (typeof currency.scale !== "number") {         // scale: number, required
  throw new Error("CRITICAL: ... mandatory for financial calculations");
}
if (!Array.isArray(response.data.items)) { ... }  // items: T[], required
```

Both were in this codebase; both are gone. A guard sitting directly on a
contract read is reported like any other finding — there is no "trust
boundary" exemption. `--exclude-boundary-checks` separates them out for
reading a diff, not for suppressing them.

What is NOT a finding is a check on something the contract genuinely leaves
open: `!currency` after a cache lookup that can miss, `accounts.length === 0`
on an array that may legitimately be empty, `!name` where `""` is a legal
value. Several of the fixes here kept exactly those halves and deleted only
the re-derivation beside them.

## Where a guarantee gets dropped

Five carriers, all asking the same question — is this declaration wider than
the contract value flowing into it?

| Carrier                                 | Example                                                               |
| --------------------------------------- | --------------------------------------------------------------------- |
| **field** on a view model or props type | `interface RowVM { status: string }` fed by a contract enum |
| **parameter**                           | `durationOrDash(ms: number \| null)` called only with required fields |
| **local** annotation                    | `const name: string \| undefined = account.entity.name`               |
| **return type**                         | `function f(a): string \| undefined { return a.entity.name }`         |
| **cast**                                | `account.entity.name as string \| undefined`                          |
| **collection element**                  | `const names: (string \| null)[] = [account.entity.name]`             |

Field constraints resolve to a **fixed point**, because a guarantee survives
being copied: a view-model field fed from another view-model field whose own
writes are all contract-constrained still carries the contract's guarantee.
A single pass resolves such a write to a local field rather than a client
property and skips it in silence — which is exactly how
one such field was missed in practice — a view model mirroring a query type
field for field — surfacing only when narrowing its source broke the
typecheck.

A shape excluded as produced-outside-literals proves **nothing**, not even
transitively: its census is incomplete, so letting it seed the fixed point
would launder a guarantee it never had into every field downstream.

## What counts as a guarantee

Read off the generated client, per field:

| Kind                | Where it comes from                            | Example evidence                           |
| ------------------- | ---------------------------------------------- | ------------------------------------------ |
| `positive`          | doc comment                                    | `Amount in minor units (must be > 0)`      |
| `non-negative`      | doc comment                                    | `Counts are non-negative.`                 |
| `range`             | doc comment                                    | `Site identifier (1-31, per REQ-004)`      |
| `non-empty-array`   | doc comment, on an array field                 | `at least one is required`                 |
| `enum-member`       | the field's type is a union of string literals | `EntityScope` = `HOUSE \| CLIENT \| GROUP` |
| `required-non-null` | the field is neither optional nor nullable     | `'created_ids': Array<string>`             |

`contract-fidelity dead-code --contracts` prints the
whole index. The doc patterns are prose heuristics, so auditing them in one
pass is what keeps them honest.

## What counts as a dead guard

Only a check the guarantee makes **statically decidable** — always true or
always false. This is the line that decides whether the rule is worth having:

| Guarantee      | Guard                                  | Verdict                                                                        |
| -------------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| `must be > 0`  | `amount > 0`                           | always true — reported                                                         |
| `must be > 0`  | `amount === 0`                         | always false — reported                                                        |
| `non-negative` | `count >= 0`                           | always true — reported                                                         |
| `non-negative` | **`count > 0`**                        | **undecided — never reported.** Zero is legal, so this is a real presence test |
| `1-31`         | `siteId > 31`                          | always false — reported                                                        |
| `1-31`         | `siteId > 10`                          | undecided                                                                      |
| required field | `x ?? fallback`, `x?.y`, `x === null`  | always decided — reported                                                      |
| required field | **`!x`** on a string or number         | **not reported.** `""` and `0` are falsy and legal                             |
| enum union     | `default:` after every member is cased | unreachable — reported                                                         |
| non-empty      | `rows.length > 0`, `!rows.length`      | always decided — reported                                                      |

Runtime type tests are decided the same way, because re-establishing at
runtime what the contract already fixed is the commonest thing people do with
a value that has been widened to `unknown`:

| Guarantee        | Guard                       | Verdict                 |
| ---------------- | --------------------------- | ----------------------- |
| `scale: number`  | `typeof scale === "number"` | always true — reported  |
| `scale: number`  | `typeof scale === "string"` | always false — reported |
| `tags: string[]` | `Array.isArray(tags)`       | always true — reported  |

Also reported: `Math.max(0, x)` and `Math.abs(x)` on a value already known
non-negative — a clamp that can never clamp.

## One thing deliberately left alone

**Boundary assertions.** A guard sitting directly on a contract read, with
nothing widened in between, is a different claim:

```ts
if (typeof currency.scale !== "number") {
  throw new Error("CRITICAL: ... mandatory for financial calculations");
}
```

The TypeScript type is a compile-time fiction over an HTTP response, and
verifying it loudly at the edge is a defensible position. This tool's thesis
is narrower — that a _widening_ is the only reason a check looks necessary —
so these are out of scope by default. `--include-boundary-checks` lists them
for a team that wants to argue about them separately. With the widened cases fixed, this
repo has 0 of the former and 21 of the latter.

**Validators.** A parameter that asks for anything is not a guarantee that
went missing:

```ts
function isObject(value: unknown): value is Record<string, unknown>;
function requireStringIdentifier(value: unknown, field: string): string;
```

Widening is the _accidental_ loss of a specific type. Declaring `unknown` is
deliberate — the author is taking responsibility for checking, and the checks
inside are the point of the function. A type-predicate return type, or a bare
`unknown`/`any` parameter on a function that throws, marks a validator. Kept
narrow on purpose: `accounts: unknown[] | undefined` is not a bare `unknown`,
and a function returning a default asserts nothing, so both stay in scope.

## Soundness: every writer, not just the one we followed

A guard inside a helper is dead only if **every** call site hands it a
guaranteed value. `textOrDash(value: string | null | undefined)` called
eleven times with contract-required fields and once with a genuinely nullable
local has a live `value == null` branch. Before reporting anything on the
callee side, the scanner re-derives the verdict at every known call site and
drops the finding unless they all agree. A parameter with no known callers,
a caller passing an unconstrained value, a spread argument, or a call with
the argument omitted all mean "unproven", and unproven is silent.

Fields work the same way: a guard on `vm.entityType` is dead only if every
write into that field supplies a guaranteed value. A spread (`{ ...other }`),
a JSX spread, or any write that cannot be resolved disqualifies the field
outright, because an unaccounted writer could supply anything.

Both censuses deliberately **include test files**, even though tests are never
scanned for origins: a test that passes `null` proves the branch is reachable.

## Deliberately out of scope

- **Test files** as violation sites — a test constructs out-of-contract
  values on purpose, so a guard there is not dead.
- **Hedged prose.** `Must be greater than zero unless the zero_amount
directive is present` guarantees nothing, and neither does `Non-empty means
the event is excluded from matching` — the second states an implication,
  not a promise. Both are read as "no constraint".
- **More than two call hops.** Past that the odds the value is still the same
  value fall faster than the odds of finding a bug.
- **Library parameters.** A widened signature in `node_modules` is not ours
  to fix.

## Commands

```bash
contract-fidelity dead-code                     # ratchet check (chained into `pnpm run lint`)
contract-fidelity dead-code --list       # every violation, with full context
contract-fidelity dead-code --contracts  # audit the constraint index
contract-fidelity dead-code --list --include-boundary-checks
contract-fidelity dead-code --json       # machine-readable
contract-fidelity dead-code:update-baseline     # down-only ratchet
```

The scan builds a real TypeScript program from `tsconfig.app.json` (~4s); it
needs the checker to follow a value across a call, and there is no honest
regex substitute.

`.narrowing-loss-baseline.json` records the legacy backlog per file. The
check fails when a file exceeds its baseline, or when a file not in the
baseline has any violation. `--update-baseline` refuses to raise a count
without `--force`.

If no `@acme` declarations are in the program (e.g. before
`pnpm install`), the scanner **fails loudly** rather than passing vacuously:
the whole policy is defined by those contracts.

## Fixing a finding

Two options, in order of preference:

1. **Delete the dead branch.** Usually right when the widened signature is a
   local helper with one or two callers.
2. **Keep the contract type on the signature.** `scope: EntityScope` rather
   than `scope: string`; `tags: string[]` rather than `string[] | null`. The
   guard then becomes visibly redundant and
   `@typescript-eslint/no-unnecessary-condition` takes over from here.

Raising the baseline is not an option.

## `widening` — the sibling check

Same inputs, same write census, one rule removed: no dead guard is required.
A field is reported when

- every write into it comes from a contract field carrying a guarantee, and
- the field's own declared type has dropped that guarantee.

Excluded on top of the shared rules: shapes **declared inside test files**
(a test's own fixture is not a view model the app ships) and fields with **no
type annotation** (nothing was widened — the inferred type _is_ the source
type).

```bash
contract-fidelity widening
contract-fidelity widening --list
contract-fidelity widening:update-baseline
```

The fix is always the same shape — narrow the field to what the contract
already promises:

```ts
-  entityName: string | undefined;   // <- entity.name, required non-null
+  entityName: string;
-  valuationRole: string;            // <- valuation_role, an enum union
+  valuationRole: ValuationRole;
```

Expect it to surface redundancy the type checker could not previously see:
once the field is narrowed, `@typescript-eslint/no-unnecessary-condition`
starts flagging the `??` and `!== undefined` that were built on it. That
handoff is the point.
